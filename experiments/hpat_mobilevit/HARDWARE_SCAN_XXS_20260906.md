# HPAT XXS 单因素硬件扫描

## 协议与修复

- 数据目录：`results/hpat_mobilevit/hardware_scan_xxs_v1`。
- MobileViT-XXS 完整 trace，192×192，batch=1；每个点运行冷启动及预热各一帧；表格取预热帧，不是多次随机重复均值。
- 映射固定 H3：Linear、1×1 Conv、QKᵀ/AV 光子化；其余算子走电子路径。每个点另跑匹配 D0。
- 基准：2 tile×2 core、每核物理 16×16、5 GHz、64 GB/s DRAM、1 MiB 权重缓存、8 MiB 激活 scratchpad、256 GB/s 片上带宽、10 TOPS 电子侧。
- 写环时间10ps，原有每环写入能耗保持；扩大阵列会增加单块写入能耗。每个核心一个写入通道，随核数一起调整。
- 所有存在域全程开启；关闭 DMA 摊销、理想输入重叠、归约重叠、部分和驻留及门控优化。
- 新增独立 `weight_cache_block_shape=[16,8]`，权重缓存始终为128B行。光子大块组装多个缓存行，D0不再随光子阵列改变其DMA粒度。动态光子权重读取仍按物理块大小计费。
- 每个扫描点重新构造 SimPhony 成本后端；核数摘要改为计算值而非写死4。
- 原有未指定缓存行形状的配置保持历史默认行为；没有覆盖旧结果。

## D0 对照

纯光子变化下 D0逐位不变：0.764859ms、2.661252mJ，程序中有断言。

| 共同存储变化 | D0时延 ms | D0能耗 mJ |
|---|---:|---:|
| 基准 | 0.764859 | 2.661252 |
| DRAM 32GB/s | 1.124987 | 2.769291 |
| 权重SRAM 0.5MiB | 1.541604 | 2.996803 |
| 权重SRAM 2MiB | 0.492209 | 2.543469 |

所有扫描点的HPAT均未优于其匹配D0的端到端时延或能耗。

## 解读

1. 堆核不是免费收益：4→8核仅降10.7%时延，却增20.5%能耗，存在共享搬运和串行执行瓶颈。
2. 32×16是值得跟进的延迟/能耗折中：K维分块减少，片上搬运与归约开销下降；但激光、保持和写入能耗增加。−0.24%的总能耗变化应解读为基本不变，不能声称稳健节能。
3. 32×32是本次单因素点中最低时延，但以更高能耗/功率换取。不是全设计空间最优。
4. 降频降低平均功率，却延长推理与静态积分；本模型中2.5GHz的单帧能耗反而增加。
5. SRAM容量有显著缓存阈值效应：0.5/1/2MiB时HPAT预热命中率约0.039%/74.0%/100%。2MiB消除了更多权重DMA启动开销，但MRR仍在层间替换，写环事件保持9810次，不能说权重永久驻留在光子阵列。
6. 同核数不同tile组织结果完全一样，是当前模型未充分刻画层级互连差异的表现，不是证明真实硬件等价。

## 必须保留的局限

- SRAM访问单位能耗、电子静态功率和片上带宽固定；未新增CACTI估计。因此SRAM容量点是条件敏感性，不是完整物理资源净收益。
- 2MiB相对1MiB账本省0.388mJ；仅额外约0.304W漏电在其1.278ms执行窗口积分，就足以抵消这一节能量（尚未考虑额外动态成本）。
- 光子后端面积估计：基准3.822mm²，32×16为5.665mm²（约+48%），32×32为6.327mm²。不是等面积比较，也不含完整电子/存储布局。
- 更大阵列引入的实际波长间隔、串扰、热漂移、供电、10ps整块写入可实现性未验证。
- 每次传输100ns及全程激光开启是模型假设；优化调度、门控或真实DMA批量传输可能改变排序。
- 仅XXS/H3，不自动推广到XS/S、H1、LT或实际手机。

## 验证与复现

- 48项测试通过，3个依赖弃用警告。
- 24案例、48帧，2,871,252条事件通过资源/权重/部分和时序和动态能耗分账检查。
- 输出包括每点有效配置、器件成本、完整压缩时间线、分层与分项数据、源码指纹、trace哈希、核成本缓存。
- `warm_comparison.csv` 包含平均功率、面积及相对变化；`completion.json` 保存 aggregate 哈希。

从项目根目录运行（必须使用新输出目录）：

```powershell
python -B -m experiments.hpat_mobilevit.run_hardware_scan --output results/hpat_mobilevit/hardware_scan_xxs_next
```

下一步优先验证32×16的器件可行性与多模型收益；2MiB缓存需补齐面积、漏电和访问成本后再考虑组合，不建议直接采用8核或32×32作为节能配置。
