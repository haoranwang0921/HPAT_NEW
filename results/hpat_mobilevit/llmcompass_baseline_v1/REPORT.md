# LLMCompass 电子基线 A/B（XXS, warm）

日期：2026-09-10　｜　工具：LLMCompass（Princeton, ISCA'24）+ SCALE-Sim 2.0.2　｜　Windows

## 1. 两条基线

| | A（同规格真实基线） | B（外部参照） |
|---|---|---|
| 名称 | HPAT-matched electronic baseline | NVIDIA A100(80GB)x4 |
| 核数 / 频率 | 4 核 / 10 GHz | 128 核 / 1.41 GHz |
| 脉动阵列 | **32×32 INT8** | 16×16（fp16 配置） |
| 片上缓冲 | 25 MiB @ 260 GB/s | 40 MB @ 5120 B/cyc |
| DRAM | **64 GB/s** | 2048 GB/s |
| 来源 | 由 `configs/GA100.json` 覆盖频率/核数/阵列/存储参数得到，与冻结 P0 逐项对齐 | 仓库自带 |

A 的设计意图：**与 HPAT 同规格**，因此 A 与当前 D0 的差异只反映"调度与存储层级建模方式"，而非硬件规格。

## 2. 方法

- 输入：`trace_v1/xxs/operator_trace.jsonl`（581 ops），矩阵类算子（Linear / MatMul / groups==1 的 Conv2d，trace 已给出 im2col 形式 M/K/N）。
- 每个不同形状调用一次 LLMCompass 的脉动阵列时序模型（`heuristic-GPU`，查表未命中时现场调 SCALE-Sim），按形状缓存。
- 覆盖：**97.28% MAC**（83 个算子，204,318,464 MAC）。覆盖外 = 7 个 depthwise 卷积（5,723,136 MAC，2.72%），LLMCompass 无 depthwise 模型，**显式排除，不静默丢弃**。
- 时延为**逐算子串行求和**（保守口径，不含算子间重叠）。
- **能量不可用**：`heuristic-GPU` 路径未设置 `energy` 字段，故本轮无能耗对照（列为后续项）。

## 3. 结果

| 口径（XXS warm, ms） | 数值 | A / 该值 | B / 该值 |
|---|---:|---:|---:|
| **A** LLMCompass 同规格 | **0.186645** | 1.00× | 13.51× |
| **A2** LLMCompass 移动级（1.4 GHz / 16×16，见 `a2_llmcompass_1p4ghz_16x16/REPORT.md`） | **0.395301** | 2.12× | 28.61× |
| **A3** LLMCompass 边缘合理（见 `a3_llmcompass_edge/REPORT.md`） | **0.607594** | 3.26× | 43.98× |
| **B** LLMCompass A100 级 | **0.013816** | 0.07× | 1.00× |
| 当前 D0（手写标量 roofline，主机总时延） | 0.492209 | **0.38×** | 0.03× |
| 当前 D0（仅 `electronic_dynamic` 计算项） | 0.079280 | 2.35× | 0.17× |
| HPAT H3（P0 冻结） | 0.799543 | **0.23×** | 0.02× |
| HPAT H3 光路并集（阶段并行） | 0.064300 | 2.90× | 0.21× |

**HPAT H3 相对各电子基线的倍数**：A1 4.28× / A2 2.02× / **A3 1.32×** / D0 1.62× / B 57.87×。

⚠️ **结论对电子基线的片上带宽高度敏感**：A2（256 GB/s 片上）→ A3（44.8 GB/s 片上）仅此一项就使电子基线时延 +54%，
H3 的差距随之从 4.28× 收到 1.32×。而真实移动 NPU（Coral / Hexagon / ANE）的片上带宽**均未公开**。
任何引用单一倍数的说法都不成立，必须给敏感性区间。

## 3b. S 模型（MobileViT-S，256²，5.58 M 参数，1,964,262,400 矩阵类 MAC）

| 口径 | ms | 占自身峰值 |
|---|---:|---:|
| **A3** 边缘合理（4 核 / 1.4 GHz / 16×16 / 4 MB / 44.8 GB/s 片上） | **3.173378** | **43.2%** |
| **B** A100 级 | **0.047463** | **89.6%** |
| 当前 D0（手写 roofline） | 2.412991 | — |
| HPAT H1（P0 冻结） | 3.789632 | — |
| HPAT H3（P0 冻结） | 5.339218 | — |

覆盖 98.17% MAC（83 算子）；覆盖外 7 个 depthwise（36,569,088 MAC = 1.83%）。

**倍数**：H3/A3 = **1.68×** ｜ H3/D0 = **2.21×** ｜ A3/D0 = 1.32×（A3 更慢）｜ H3/B = 112.5×

### 发现一：利用率随模型规模显著上升

| 模型 | 矩阵类 MAC | A3 时延 | **A3 占自身峰值** | B 占自身峰值 |
|---|---:|---:|---:|---:|
| XXS | 204.3 M | 0.607594 ms | **23.5%** | 32% |
| S | 1964.3 M | 3.173378 ms | **43.2%** | **89.6%** |

S 的 MAC 是 XXS 的 **9.61×**，时延只涨 **5.22×** ⇒ 模型越大，阵列填充越充分、电子基线越有效率。
（XXS 的 K/N 太小，连 16×16 阵列都填不满；S 的通道更宽，填充率接近翻倍。）

### 发现二：HPAT 的相对劣势随模型规模**扩大**

| 对照 | XXS | S | 方向 |
|---|---:|---:|---|
| H3 / A3（边缘合理基线） | 1.32× | **1.68×** | 差距变大 |
| H3 / D0（手写 roofline） | 1.62× | **2.21×** | 差距变大 |

这与论文原先"映射比例更高（S 77.2% > XXS 67.8%）⇒ 加速比更大"的预期**方向相反**：
实测是模型越大，电子基线的填充效率提升越快，而光子侧的阶段开销与搬运不随规模同等下降。

> 以上两点共同支持同一个机制结论：**MobileViT 系列的吞吐由其"形状 × 阵列填充"决定，而不是峰值算力**；
> 因此"提高映射比例换取更大加速比"这条论证链在数据上不成立。

**A2 补充（移动级 1.4 GHz / 16×16）**：峰值 1.4336 TMAC/s，实测 0.517 TMAC/s ⇒ **占自身峰值 36.1%**；
而 A1（32×32 @10 GHz）峰值 40.96 TMAC/s、实测 1.095 TMAC/s ⇒ 仅 **2.7%**。
A2 峰值低 28.6×，时延却只慢 2.12× ⇒ **利用率高 13.4×**。HPAT H3 相对 A2 为 **2.02× 慢**
（相对 A1 为 4.28×，相对手写 D0 为 1.62×）。

**两个头条结论**

1. **HPAT 相对同规格真实电子基线慢 4.28×**（H3 0.7995 vs A 0.1866）。此前相对手写 D0 是 1.62×。审稿人担心的"若 8× 降到 3–4× 则端到端仅约 1.5×"在真实基线面前更保守——**真实差距比审稿人估计的还大**。
2. **当前 D0 自身的两半在朝相反方向偏**：逐算子看，A 比 D0 的 roofline 计算慢 2–14×（例：M=9216,K=27,N=16 → A 0.010844 vs roofline 0.000796，慢 13.6×）；但**总时延**上 A 比 D0 快 2.64×（0.1866 vs 0.4922），因为 D0 把每个算子的输入/输出都按 DRAM 串行计费（0.4078 ms，占其 82.9%），而 LLMCompass 按分块 tiling + 双缓冲 SRAM 建模、片内复用。

**逐算子样例**（ms）

| M | K | N | A（32×32/10GHz） | B（A100） | D0 roofline |
|---:|---:|---:|---:|---:|---:|
| 9216 | 27 | 16 | 0.010844 | 0.000599 | 0.000796 |
| 9216 | 32 | 16 | 0.006943 | 0.000376 | 0.000944 |
| 2304 | 32 | 24 | 0.002054 | 0.000173 | 0.000354 |
| 576 | 432 | 48 | 0.005255 | 0.000404 | 0.002389 |

## 4. 一个值得注意的旁证

A 在 204.3 M MAC 上耗 0.1866 ms ⇒ 约 **1.09 TMAC/s**，而 4×32×32×10 GHz = 40.96 TMAC/s 峰值 ⇒ **A 只跑到自身峰值的 2.7%**。
与本项目此前测得的 HPAT 光子阵列墙钟利用率 **5.4%**（计算期 19.4% × 占空比 27.8%）属同一量级。

⇒ **在 MobileViT 这批形状上，两类架构都被"填不满阵列"所支配**；差距主要来自开销结构（搬运、转换、常开），而不是峰值吞吐。这一点与 R1-1 的批评方向一致。

## 5. 证据边界

- A 是**由 GA100 配置覆盖参数得到的模型**，不是流片或实测设备；B 同理。
- 逐算子串行求和是保守口径；LLMCompass 的 tiling/双缓冲假设比 D0 的"每算子全量过 DRAM"更乐观——**两者是不同存储假设，必须同时报告，不能只挑一个**。
- 能量缺口未补（`heuristic-GPU` 不设 `energy`）。
- depthwise 与向量/归一化算子不在覆盖内；H3 的完整对照需另补向量项。
- 1 个模型（XXS）；XS/S 未跑。
- 形状缓存：`shape_cache.json`（重复运行不再调 SCALE-Sim）；`wall_s` ≈ 1000 s / 919 s。

## 6. 复现

```
python -B -m experiments.hpat_mobilevit.run_llmcompass_baseline --config a --models xxs
python -B -m experiments.hpat_mobilevit.run_llmcompass_baseline --config b --models xxs
```
依赖：`scalesim==2.0.2`（**必须 v2**）。配置见 `experiments/hpat_mobilevit/llmcompass_configs/matched_a.json`。
