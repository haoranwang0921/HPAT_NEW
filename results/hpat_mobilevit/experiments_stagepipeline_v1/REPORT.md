# 光子三段时序：串行 vs 阶段并行（Batch-5）

日期：2026-09-10。P0 主点（32×32 / 10 GHz / 25 MiB / DRAM 64 GB/s），MobileViT-XXS/XS/S 形状 trace，
D0 与 H1/H3 映射，cold/warm 各一帧。目录 `experiments_stagepipeline_v1/{b5_serial,b5_pipe}`。

## 1. 为什么做这件事

此前"光子计算链比电子慢 4.2×"的结论，来自把 DAC 编码 / 光算 / ADC 转换三段的**服务时间相加**
（各 0.0715 ms，合计 0.2146 ms）再与 D0 全部电子计算（0.0508 ms）比较。该比较有两处失真：

1. **三段被建模为同一核上的串行链**（`streaming.py::execute_core_block`，三段共用资源名 `core_{i}`，
   而 `event()` 对同名资源强制互斥）。源头在 SimPhony：`onnarchsim/simulator.py:311-316` 把
   `compute_latency_s + operand_encoding_latency_s + conversion_latency_s` 相加。
2. 拿**三段之和**（服务时间）去比 D0 的**单一计算项**，量纲不一致。

物理上编码器、光阵列、转换器是**三套独立器件**（本配置 `dac_count=256`、`adc_count=128`、`mrr=4096`），
真实流水线可对不同输入向量并发工作。

## 2. 改动

- `mobile_profile.py`：新增开关 `photonic_stage_pipeline`（默认 **False** = 历史行为）。
- `streaming.py`：开关开启时三段各占独立资源（`dac_/optic_/adc_<core>`），完成时刻取
  `max(N·t_e, t_e + N·t_c, t_e + t_c + N·t_v)`，N = 2×M（两个符号 pass × M 个输入向量），
  t_* 为单向量阶段时间。**各段能量不变**，只改可重叠程度。
- `verify.py`：校验语义细分——新调用以"前一调用全部结束"为门（`core_end`），
  同一调用内下游段只需晚于上游段**起点**，且阶段起点单调；各段自身器件时间线仍由资源互斥校验。
- 新增 `run_batch5_stage.py`；`tests/test_streaming.py` 增 3 项测试。
- 全量回归 **148 passed**；`b5_serial` 与冻结 P0 逐位一致（XXS H3 warm 0.7995425730519088 ms /
  5.8317833517746935 mJ；D0 0.4922092530012263 ms / 2.543468606300368 mJ）。

## 3. 结果（warm）

| 模型 | 映射 | 串行 ms | 阶段并行 ms | 时延 | 能耗 |
|---|---|---:|---:|---:|---:|
| XXS | D0 | 0.4922 | 0.4922 | 0.00% | 0.00% |
| XXS | H1 | 0.6297 | 0.6288 | −0.14% | −0.06% |
| XXS | H3 | 0.7995 | 0.7806 | **−2.37%** | −1.07% |
| XS | H3 | 2.5643 | 2.5502 | −0.55% | −0.25% |
| S | H3 | 5.3392 | 5.3117 | −0.51% | −0.25% |

相对 D0 的比值（时延/能耗）：XXS H3 由 1.62×/2.29× 变为 **1.59×/2.27×**。

## 4. 关键发现：光路时间原本被总线遮住 77%

XXS H3 warm 的事件并集分解：

| | 串行 | 阶段并行 |
|---|---:|---:|
| 三段并集 | 0.1151 ms | **0.0643 ms（−44%）** |
| 片上总线 sram_noc 并集 | 0.2995 ms | 0.2995 ms |
| 三段与总线重叠 | **0.0886 ms（占三段 77%）** | 0.0608 ms |
| 未重叠（真正暴露）的三段 | 0.0265 ms | **0.0036 ms** |

即：阶段流水**按设计生效**（三段并集缩短 44%，暴露时间几乎归零），但**整帧只省 2.4%**，
因为 77% 的段时长本来就和总线搬运重叠，关键路径始终是 `sram_noc`。

同口径对比：光路并集 0.0643 ms vs D0 全部电子计算 0.0508 ms → **1.27×**（不再是 4.2×）。

## 5. 边界

1. 这是**时序保真度**修正，不是架构改动；`b5_pipe` 假定编码/转换器件可与光阵列并发，需器件级依据。
2. 未实现跨调用的流水（`begin` 仍取 `core_ready`），收益仅限单次调用内部。
3. 未改 D0；两变体的 D0 逐位一致，可作对照。
4. 阵列利用率仍然很低：三段并集 0.0643 ms 内完成 142.36 M 映射 MAC（H3），
   聚合约 **2.2 TMAC/s**，而 4 核理论峰值为 4 × 32×32 × 10 GHz = 41 TMAC/s，即**约 5%**。
   主因是权重块小（K 受 32 波长限制、N 受正负行配对限制到 16 逻辑），这是下一步的真正杠杆，
   属架构问题而非时序问题。
5. 全部数值为架构级事件模型输出，无硅实测、无准确率含义。

## 6. 阵列利用率分解（XXS / H3 / warm / 阶段并行）

由 `events.jsonl.gz` 的每次调用重建 (M, K_block, N_block)：2909 次调用、142,359,296 有效 MAC、
715,284 个核周期（每次调用 2M 周期 = 两个符号 pass）。

| 层 | 数值 |
|---|---:|
| 峰值（32 波长 × 32 行 × 10 GHz） | 1024 MAC/cycle |
| − 权重行配对（± 各占一行，`physical_N = 2·logical_N`） | ×1/2 |
| − 双输入 pass（`input_sign_passes = 2`） | ×1/2 |
| − K 填充不足（按 M 加权均值 25.6/32 = 80%） | ×0.80 |
| **计算期实测** | **199 MAC/cycle = 19.4%** |
| **占空比**（4 核周期 / 墙钟 × 4） | **27.8%** |
| **墙钟利用率** | **5.4%** |

填充分布（按 M 加权）：K 为 32 占 57.5%、16 占 33.1%、24 占 5.9%；N 为 16 占 94.6%（N 填充已 97%，几无空间）。
周期占比最高的组合是 (K=32, N=16) 54.9% → 256 MAC/cycle，与 (K=16, N=16) 31.8% → 128 MAC/cycle。

**结论**：计算期损失主要来自**非负编码**（1/4 = 行配对 1/2 × 双 pass 1/2），其次才是 K 填充；
而墙钟上还有 72.2% 的时间阵列根本没在算。两条战线必须分开攻。
